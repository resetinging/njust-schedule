# 用户数据每日自动同步（2026-11-01）

> 状态：已实现，本地未提交、未发布。版本：**v1.11.0**（BUILD `2026.11.27.1`）。
> 范围：Go/WebGo 后端 + 微信小程序。本文不含任何密码、Cookie、Token 或真实账号信息。

## 1. 目标

把“用户数据从教务获取”的路径，从“每个用户登录/手动刷新各自触发”改为**与服务端空教室查询同款逻辑**：

- 服务端每日凌晨批量预热用户数据，并写入 MySQL 快照；
- 小程序只读本服务 API，不直连教务；
- 默认关闭实时回源刷新，避免用户侧绕过批量缓存反复访问教务；刷新入口保留，普通页面只重载服务器快照，考试页刷新作为明确产品能力单独开放；
- 首次登录、换学期等“服务端缓存未命中”场景，允许服务端兜底抓取一次（等价于空教室缓存未命中回源）。

## 2. 当前行为

### 2.1 每日批量预热

- 任务：`user-data-daily-sync`（`internal/httpapi/user_sync.go`、`jobs.go`）。
- 时间：北京时间 **00:20**；服务启动时也补跑一次（已同步用户自动跳过，行为与空教室预热一致）。
- 对象：`authn.PersistentStudentIDs` 中有持久教务 Cookie 的用户；默认只处理近 30 天有持久会话记录的用户。
- 内容：复用登录预抓步骤——本科：校历、课表、考试、成绩、四六级、评教、培养方案、学籍；研究生：课表、成绩、考试。
- 并发：默认 2 个用户并发，受全局 `JW_MAX_CONCURRENT`（默认 4）约束；每个用户启动前 0–2 秒随机错峰。
- 失败语义：单项失败保留旧数据、不更新该项版本；只有全部成功才写 `data_cache_at` 标记。
- 批量任务不盲目用密码重登：持久 Cookie 失效的用户记为失败，等用户登录时兜底；避免 SSO 风控。

### 2.2 登录与查询

- 登录成功后若 `data_cache_at` 已是“本次计划同步之后”的时间 → **不触发教务预抓**，直接读 MySQL。
- 若没有缓存标记（首次登录、新用户、或批量未覆盖） → 后台预抓一次后返回；这是缓存未命中回源，不是手动刷新。
- 普通查询（课表/考试/成绩/评教/四六级/培养方案/学籍）继续优先读取 MySQL 快照。
- 用户最多看到延迟到下一次凌晨的数据；批量失败时保留最近一次成功快照。

### 2.3 手动刷新策略

- 小程序保留课表、成绩（含研究生/四六级）、评教、培养方案的刷新入口；普通刷新只读取服务器快照，不访问教务。考试刷新实时访问教务。
- 后端 `/api/refresh-exams` 独立于全局开关，要求登录并实时访问教务，按用户 3 次/分钟限流；成功返回 `refreshed:true`。
- 后端 `/api/refresh-schedule`、`/api/refresh-all`、`/api/refresh-grades`、`/api/refresh-cet`、`/api/refresh-evaluations`、`/api/refresh-calendar`、`/api/refresh-programme`、`/api/refresh-profile` 默认不访问教务，返回：
  `{"success":true,"refreshed":false,"message":"数据每日凌晨自动更新，当前为服务器已同步数据"}`
- `ALLOW_LIVE_REFRESH=1` 可临时恢复上述其他刷新接口用于排障，默认保持关闭，不影响考试刷新。
- 小程序通过 `refreshed:false` 区分“服务器快照提示”和“实时刷新成功”：前者显示后端真实提示并重新读取快照，不再误报刷新成功或清空当前数据。
- 小程序考试刷新使用 `force:true` 绕过离线短路；离线且有记忆密码时自动重登后重试，无记忆密码时提示重新登录。
- 启动状态校验强制绕过离线短路；自动重登成功后立即重新预取数据并激活当前页面，反馈未读消息和空成绩缓存随会话恢复。
- 研究生课表优先当前学期，避免教务学期选项倒序时误选未来学期；考试页每次进入按 30 分钟时间窗自动静默刷新，并与手动刷新共享时间窗。

## 3. 配置项

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `USER_DATA_DAILY_SYNC` | 开启（空值视为开启） | 设为 `0/false/off` 关闭每日用户数据批量同步 |
| `USER_DATA_SYNC_CONCURRENCY` | 2 | 用户级并发（1–8） |
| `USER_DATA_SYNC_LOOKBACK_DAYS` | 30 | 只同步最近 N 天活跃的持久会话用户；0 表示不限制 |
| `USER_DATA_SYNC_MAX_USERS` | 0 | 单次任务最多处理的用户数；0 表示不限制 |
| `ALLOW_LIVE_REFRESH` | 关闭 | 设为 `1` 才允许其他刷新接口回源教务；考试刷新不受此开关限制 |

每日任务固定北京时间 00:20；启动即补跑。没有新增数据库迁移，同步标记复用 `user_settings.data_cache_at`。

## 4. 与空教室的一致性

| 维度 | 空教室 | 用户数据 |
|---|---|---|
| 定时预热 | 每日 00:02 + 启动补跑（`FREE_CLASSROOM_PREWARM`） | 每日 00:20 + 启动补跑（`USER_DATA_DAILY_SYNC`） |
| 普通请求 | 只读服务端缓存 | 只读 MySQL 快照 |
| 缓存未命中 | 服务端同步访问教务后缓存 | 登录/首次使用由服务端兜底预抓一次 |
| 手动刷新 | 无 | 各业务页保留刷新入口；考试实时回源并限流，其他刷新只读取服务器快照 |
| 缓存粒度 | 按查询参数缓存到次日 00:02 | 按用户持久快照；每日批量刷新 |
| 失败 | 不缓存失败结果 | 保留旧快照、不写成功标记 |

## 5. 测试与限制

- 后端新增：同步标记按计划时刻判定、用户活跃回溯、刷新接口默认关闭/提示、`ALLOW_LIVE_REFRESH` 开关；全量 `go test -count=1 ./...` 与 `go vet ./...` 通过。
- 前端回归：现有 API/导航/课表/考试/成绩/评教/空教室/图书馆/UI/字体/图标/DSL 测试与 `verify_wxml`/`verify_miniapp`/`verify_privacy` 通过。
- 限制：
  - 未在真实教务环境跑批量任务；测试使用纯函数与桩件，上线前需在测试账号上验证一次批量预热与登录兜底。
  - 用户数据最多延迟到下一个凌晨；批量失败或持久 Cookie 失效时，用户可能看到最近一次成功快照。
  - 批量任务目前为单实例进程内任务（当前容器 `maxNum=1`）；横向扩容前需要选主/分布式锁。
  - 首次部署或服务在 00:20 前重启时，启动补跑可能集中访问教务，需观察上游负载。
  - 非考试刷新可通过 `ALLOW_LIVE_REFRESH=1` 临时回退为实时抓取，但默认发布必须关闭；考试刷新始终需要登录并受用户级限流。
