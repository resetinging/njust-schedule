# 后端存储教务密码 · 企业级方案（规划稿）

> 背景：会话在进程内存里，服务重启/多实例都会导致登录态丢失，用户必须重新登录。
> 目标：让"重启后自动恢复登录"成为可能。本文只讲方案与边界，不含实现。

## 一、先说根本矛盾

登录智慧理工**必须用明文密码**（要发给学校的登录接口），所以后端只能**可逆加密存储**，
不能用哈希。这意味着：**数据泄露的后果等同于用户密码泄露**——所以方案的重点不在"存不存"，
而在"权限、密钥、审计、可撤销"这四件事上。

## 二、三条路线对比

| 路线 | 体验 | 泄露影响面 | 工程量 | 建议 |
| --- | --- | --- | --- | --- |
| A. 不存任何凭据（现状） | 重启/失效需重登 | 无 | 0 | 保底 |
| B. 只存教务 Cookie（加密） | 重启后可恢复；Cookie 过期仍需重登 | 可被吊销，影响同一次会话 | 中 | **优先做** |
| C. 存密码（加密） | 真正零重登 | 等同密码泄露 | 中高 | 有明确产品需求再做 |

**推荐顺序：先 B，再评估 C。** 因为 B 能解决 80% 的痛点（重启掉线），
而风险面小一个数量级——Cookie 是"可吊销的会话凭证"，不是"长期密钥"。

## 三、路线 B：教务 Cookie 持久化

1. 登录成功后，把客户端的 Cookie（含 JWX 会话 cookie）与过期时间一起**加密**存库；
2. 服务启动/会话缺失时，用该 Cookie 重建客户端，先做一次轻量探活（如抓课表首页）；
3. 探活失败 → 清除该条 Cookie，标记用户"需要重新登录"，前端提示；
4. 多实例友好：只是"读一条加密记录"，天然支持横向扩容。

存储表：`session_cache(student_id PK, cookie_cipher, iv, tag, key_version, expires_at, updated_at)`

## 四、路线 C：密码加密存储（若产品坚持）

### 1. 加密
- **AES-256-GCM**，每用户独立随机 IV(12B)，AAD 绑定 `student_id`（换行拼接防迁移攻击）；
- 密文结构：`key_version | iv | ciphertext | tag`，全部 base64 存 single TEXT 字段；
- 密钥长度 32B，来自环境变量/KMS，**绝不入库、绝不进代码**。

### 2. 密钥管理
- 环境变量 `CRED_KEY_V1=<base64 32B>`（KMS 托管更佳）；
- 轮换：`V2` 上线的同时保留 `V1` 只读，后台任务逐条"旧钥解密 → 新钥加密"；
- 密钥泄露应急：全量作废凭据 + 强制全体重新登录 + 通知用户。

### 3. 存取与权限
- 独立表 `user_credentials(student_id PK, cipher, updated_at, last_used_at, fail_count)`；
- 业务表与凭据表**不同 DB 账号**：应用账号对该表只有 SELECT/INSERT/UPDATE（不给 DELETE，
  删除走"逻辑删除 + 后台清理"以便留存审计）；
- 解密入口只有一个函数，调用处加装饰器限制；
- `GET /api/credentials` 只返回 `{saved: true, updated_at}`，**永不回传密码**。

### 4. 使用与风控
- 只在"401 自动重登"这一条路径上解密使用；
- 自动重登同样走现有失败计数节流（学号+IP），连续失败 N 次**自动清除凭据**并要求手动登录；
- 每次使用写审计：`credential_audit(rid, student_id, action, ip, ts)`，action ∈ save/use/rotate/delete/fail。

### 5. 前端与合规
- 当前实现默认保存密码，登录页不再提供开关；退出登录保留密码，提供独立删除接口；
- 密码仅用于 24 小时内 Cookie 快速恢复和会话失效自动重登，本地复用不延长信任期；
- 隐私保护指引必须写明：收集内容（密码）、用途（自动登录）、存储方式（加密）、保留期限、删除方式；
- 旧前端发送的 `remember=false` 不会再关闭服务端默认保存策略。

### 6. 内存与日志边界（如实说明）
- 解密后的明文只活在函数作用域内，**不写日志、不进异常信息、不做缓存**；
- Python 无法保证内存"零化"，这是该方案无法消除的残余风险，需在文档与评审中写明。

### 7. 测试清单
- 单测：加密/解密往返、GCM tag 篡改必须拒绝、AAD 换学号必须解密失败、密钥轮换后新旧密文都能读；
- 集成：保存 → 重启服务 → 自动重登成功；连续失败 N 次 → 凭据被清除；
- 负向：`GET /api/credentials` 响应体里不得出现明文（用断言扫一遍 JSON）。

## 五、决策要点（需要产品/你拍板）

1. 是否接受"密码可能泄露"的残余风险？不接受 → 只能走 B；
2. 若走 C，是否同意"默认关闭 + 显式勾选"的产品形态？
3. 密钥由谁保管（云托管环境变量 or KMS）？轮换周期？
